Real-time simulation and stimulation

From offline scores to a closed loop

In tutorial 06 the network was judged sample by sample: is this 4 ms point inside a spindle or not? A stimulation experiment asks a different question: did one sound arrive while the spindle was still going on, and only one? The Portiloop paper makes this distinction explicitly [1]:

Valenchon et al. (2022), section 6.1"The performance measured in the previous section is not entirely representative of the performance on the final task. So far, we have only measured the capability of the model to annotate each data point of the signal individually. Yet, we want the ability to send one single stimulation per sleep spindle."

Between the brain and the speaker, the signal goes through a chain of stages. Coloured edges: purple for the acquisition and output hardware, blue for signal processing, orange for the network:

  1. Electrodes and ADCone sample every 4 ms (250 Hz)
  2. FIR lowpass, 21 taps40 ms group delay
  3. 60 Hz notchIIR, one biquad
  4. Online standardizationrunning mean and variance
  5. Window of 54 samples0.216 s of signal
  6. Network forward pass20 ms on the FPGA [1]
  7. Threshold and refractory ruleone stimulus per spindle
  8. Sound4 ms with a basic sound controller [1]

The filters were covered in tutorial 03 and the network in tutorial 04. Here we focus on what happens when these pieces run continuously, against the clock.

For neuroscientistsThink of the device as a participant in a reaction-time task. The "stimulus" is the spindle onset, the "response" is the sound. Part of the reaction time is perceptual (the network must see enough cycles to be confident), part is motor (the sound hardware), and part is conduction (the filters). Just as in psychophysics, you cannot remove the perceptual part without increasing errors: a lower detection threshold answers faster but also "responds" to things that are not spindles. The paper notes that each spindle cycle is "only ~60 ms long and the entire spindle is between 0.5 and 2.5 s" [1], so every few tens of milliseconds matter.

The sample stream and the 20 ms rhythm

The Portiloop samples the EEG at 250 Hz, so a new value arrives every 4 ms. The network cannot run that often: the paper reports "We measure the execution time of this architecture to be 20 ms per forward pass on the Portiloop" [1] (FPGA version). The simulation notebook encodes this as a number of samples:

FPGA_NN_EXEC_TIME = 5  # equivalent to 20 ms
ERROR_FPGA_EXEC_TIME = 0  # to be sure there is no overlap

Five samples at 4 ms each is 20 ms. ERROR_FPGA_EXEC_TIME is a safety margin (in samples) that you can add if your hardware's inference time fluctuates; it is 0 in the notebook. So at most one window can be evaluated every 5 samples. Each window is the last 54 standardized samples (int(0.218 * 250) = 54, about 0.22 s), ending at the newest sample. Consecutive windows therefore overlap by 49 samples: the network looks at almost the same stretch of signal, shifted by 20 ms.

Why eight hidden states?

The network ends with a GRU, a recurrent layer whose 7-number hidden state carries a memory of previous windows (tutorial 04). During training, the GRU was not fed overlapping windows 20 ms apart. It was fed sequences of 50 windows spaced by seq_stride_s = 0.17 s, that is int(0.17 * 250) = 42 samples or 168 ms. The paper calls this spacing time dilation: "the time-dilation (set to 168 ms by PMBO)" [1]. A sequence of 50 such windows covers about 8.4 s of EEG, which is what lets the network use context well beyond one window (the config entry 'time_in_past': 8.5).

The hidden state has therefore learned dynamics that assume 168 ms between updates. If we fed it a window every 20 ms, its memory would evolve about eight times too fast, a regime it never saw. The solution is to keep several independent copies of the hidden state and use them in turn (round robin):

$$n_\text{parallel} = \left\lfloor \frac{\text{seq\_stride}}{\text{FPGA\_NN\_EXEC\_TIME} + \text{ERROR\_FPGA\_EXEC\_TIME}} \right\rfloor = \left\lfloor \frac{42}{5} \right\rfloor = 8$$ 
    nb_parallel_runs = seq_stride // (FPGA_NN_EXEC_TIME + ERROR_FPGA_EXEC_TIME)
    print(f"seq_stride: {seq_stride}")
    print(f"FPGA_NN_EXEC_TIME + ERROR_FPGA_EXEC_TIME: {FPGA_NN_EXEC_TIME + ERROR_FPGA_EXEC_TIME}")
    print(f"nb_parallel_runs: {nb_parallel_runs}")
    stride_between_runs = seq_stride // nb_parallel_runs

Hidden state 1 sees windows ending at samples 53, 95, 137, ... (42 apart); state 2 sees the windows 5 samples later; and so on. Each state lives in the 168 ms world it was trained in, yet together they produce a fresh output about every 20 ms. The paper calls these "decoupled virtual parallel networks" [1] and shows they matter: when the time dilation is shrunk to 20 ms so that a single state must be used, "the highly deteriorated results illustrate the importance of time-dilation" [1].

For neuroscientistsPicture eight observers watching the same EEG monitor, each glancing at it once every 168 ms, with their glances staggered by 20 ms. Each observer keeps their own running impression of the last few seconds. Any single observer is slow, but at every moment one of them has just looked. Nothing is shared between observers, which is why the paper calls them "decoupled".

Three ways to fit 8 windows into 42 samples

Eight windows 5 samples apart span 40 samples, not 42, so the two extra samples must go somewhere. The code in the Portiloop ecosystem does this in three slightly different ways; all keep 8 hidden states:

WhereGaps between consecutive windows (samples)Spacing seen by each hidden state
Simulation notebook (ValidationSampler with network_stride = stride_between_runs = 5)5, 5, 5, 5, 5, 5, 5, 7exactly 42
Device software, portiloop-software (stride_counters)5, 5, 5, 6, 5, 5, 5, 6exactly 42
This website, PL.PortiloopModel.prototype.runStream5, 5, 5, 5, 5, 5, 5, 540 (an approximation)

The device code computes its gaps from the same two numbers:

        num_models_parallel = 8
        window_size = 54
        seq_stride = 42
...
        self.stride_counters = [np.floor((self.seq_stride / self.num_models_parallel) * (i + 1)) for i in range(self.num_models_parallel)]
        for idx in reversed(range(1, len(self.stride_counters))):
            self.stride_counters[idx] -= self.stride_counters[idx-1]
        assert sum(self.stride_counters) == self.seq_stride, f"{self.stride_counters} does not sum to {self.seq_stride}"

In the notebook, the extra 2 samples appear as the adder = 2 applied every 8th output (if (i+1)%nb_samp ==0) when outputs are mapped back to sample indices. The live oscilloscope below lets you switch between the three schedules.

Latency: where the milliseconds go

The paper measured each delay on the FPGA version of the Portiloop and summarized them in its Table 2 (reproduced here; "~" marks the variable part):

Table 2 of Valenchon et al. (2022) [1], "Delays measured in the Portiloop (sleep spindle configuration)".
ComponentHardware delaySoftware delay
Electrodes + ADC--
Filters-40 ms
ANN20 ms~250 (± 100) ms
Stimulus4 ms-
Total: ~314 ms24 ms290 (± 100) ms
  • Filters, 40 ms (constant). The 21-tap linear-phase FIR delays every frequency by half its length: 10 samples = 40 ms (tutorial 03). The paper designed both preprocessing branches "so that they introduce identical software delays to their respective outputs (i.e., 40 ms at 250 Hz sampling rate with FIR filters of order 20)" [1].
  • ANN forward pass, 20 ms (constant). The time to compute one output once its window is complete.
  • Stimulus, 4 ms (constant). "We measure an auditory stimulation delay of 4 ms when using a basic sound controller, for a total constant delay of 64 ms" [1].
  • Detection delay, about 250 ms (variable). The network needs to see part of the spindle before its output crosses the threshold. This is the largest term, and the paper notes that "Training a faster model is thus a potential avenue for future work" [1].

The constant part is exactly the notebook's constant_delay_s:

seq_stride = int(config_dict["seq_stride_s"]*config_dict["fe"])
network_stride = 5
nb_samp = 8
window_size = int(config_dict["window_size_s"]*config_dict["fe"])
max_time_stimulate_s = 0.25
constant_delay_s = 0.064

print(f"seq_stride: {seq_stride}")

constant_delay_s = 0.064 is 40 + 20 + 4 ms. It is added in the notebook because the notebook's dataset was filtered offline with the FIR delay already compensated (tutorial 03), so the filter delay has to be put back by hand. max_time_stimulate_s = 0.25 is the tolerance used to call a stimulation "accurate" (see below). nb_samp = 8 repeats the number of hidden states for the bookkeeping loops.

The decision rule: threshold and refractory period

The network outputs a number between 0 and 1 every ~20 ms. Turning it into stimuli needs two choices.

A threshold. An output above the threshold means "spindle". The notebook uses THRESHOLD = 0.5 (from threshold_list = {'p1': 0.2, 'p2': 0.35, 'full': 0.5} with PHASE = 'full'). The device software uses a default of 0.75 ("threshold": 0.75 in DEFAULT_CONFIG_DICT, adjustable in its interface) and counts an output equal to the threshold as a detection (>=, where the notebook uses >). The paper found that, counting stimulations rather than samples, "the best such trade-off is attained at a threshold of 0.84 with our model, yielding a precision and a recall of 0.71 both", at the price of "slightly shifting the stimulation delay distribution to the right" [1].

A refractory rule. The output often flickers around the threshold at the beginning and end of a spindle, and the eight hidden states do not agree perfectly. Without a rule, one spindle would trigger a burst of sounds. The paper describes the rule [1]:

Valenchon et al. (2022), section 5"A stimulus is sent upon initial spindle detection. To avoid multiple stimuli of the same spindle, the subsequent stimulation may only occur 400 ms following the end of the spindle. If a spindle is detected again within this duration the timer is reset, and we consider it as being part of the previous spindle."

In the notebook it is implemented with two counters in samples (100 samples = 400 ms):

        for i in range(len(output_test)):
            adder = 0
            label = output_test[i]
            if (i+1)%nb_samp ==0:
                adder = 2
            if label > THRESHOLD and wait_stim == 0 and not in_spindle:
                spindle_list_stimulate.append(cur_idx)
                wait_stim = 100
                in_spindle = True
            if in_spindle and label > THRESHOLD:
                wait_in_spindle = 100#42
            if label <= THRESHOLD and wait_in_spindle <= 0:
                in_spindle = False
            cur_idx += network_stride+adder
            wait_stim -=network_stride+adder
            wait_in_spindle -=network_stride+adder

Read it as a small state machine: a stimulation is sent when the output crosses the threshold while we are not "in a spindle"; we stay "in the spindle" as long as above-threshold outputs keep coming less than 400 ms apart. The device software implements the same idea with a wall clock (self.wait_t = 0.4 # 400 ms and if ts - self.last_detected_ts > self.wait_t: in SleepSpindleRealTimeStimulator). The 400 ms value is a design choice, not a property of the network: you can change it for your experiment, for example to avoid stimulating spindle trains.

For neuroscientistsThis is a refractory period with a twist: it is measured from the last time the detector said "spindle", not from the last stimulus. A long spindle therefore receives one sound, however long it lasts, and the detector re-arms only after 400 ms of "no spindle". It plays the same role as the dead time of a spike detector that prevents one action potential from being counted twice.

How the statistics are computed (paper definitions, section 6.1 [1]): a spindle is stimulated (true positive) if a stimulation falls inside its labelled duration, all delays included, and the delay is measured from the spindle onset to the first such stimulation; every other stimulation is false. "Within 250 ms" counts stimulated spindles whose delay is at most max_time_stimulate_s = 0.25, the notebook's tolerance. The first 5 s of each recording are not used for stimulation (see the note below).

Note on start-upThe online standardizer starts with no knowledge of the signal's variance; with ασ = 0.001 its estimate needs on the order of 1000 samples (4 s) to settle, and in that period the network sees badly scaled input and tends to fire. The widget therefore ignores the first 5 s. This warm-up is a choice of this widget, not something we found in the notebook; on a device, start stimulating only after the signal has been streaming for a few seconds.
Synthetic dataThe recording is a didactic signal with smooth, waxing spindles. Its numbers (on the order of 0.4 s median delay at threshold 0.5 in our tests) are not those of real EEG. For real performance figures, run the notebook (next section) on real annotated data converted to the dataset format, or use the values of the paper (Table 2 above; precision and recall of 0.71 at threshold 0.84).
Under the hoodThe JavaScript in this page uses PL.filters.FIR, PL.filters.Biquad with PL.filters.PORTILOOP_NOTCH, PL.OnlineStandardizer and model.step(window, h) from the site library. We checked offline that, with the uniform schedule, its outputs equal PL.preprocess followed by model.runStream on the same data (largest difference 3e-8, float rounding). Each model.step takes a few milliseconds in JavaScript; if your computer cannot keep up at 5x, the widget slows down rather than skipping samples and says so in the status line.

Which part of the signal drives a decision? (Captum)

The last section of the notebook ("Interpretation of the results with Captum") asks which samples of the input pushed the output up. It uses Integrated Gradients [3] from the Captum library [2]: the input is morphed gradually from a baseline (here, a sequence of windows taken elsewhere in the test set) to the real input, and the gradient of the output with respect to each input sample is accumulated along the way. Cell 19 rebuilds a sequence of seq_len = 20 consecutive windows of one hidden state (idx_batch selects the segment and offset, i_min = 98 the starting window; the comment suggests spindles at 97, 200, 281), cell 21 wraps the network so that it takes only the signal and starts from a zero hidden state, and cell 23 computes:

ig = IntegratedGradients(net_captum)
attributions, delta = ig.attribute(input, baselines=bl, return_convergence_delta=True)

Cell 24 draws the 20 windows in a grid, each coloured by the absolute attribution (red = strong influence), the last panel titled with the network's score, and saves grad_explainer.pdf. The convergence delta printed by cell 23 should be small compared with the output; if it is not, the attribution is not reliable (more integration steps are needed).

For neuroscientistsIntegrated Gradients is a "virtual lesion" study: instead of removing a brain region and measuring the deficit, it asks how much the output would change if each input sample were replaced by its baseline value, integrating over all intermediate levels. Like lesion studies, the answer depends on the control condition: a different baseline gives different maps.

Interpreting the results

  • Sample-level F1 vs stimulation precision and recall. They measure different things. A detector can have a modest sample-level F1 (it marks the second half of each spindle) and still stimulate nearly every spindle once.
  • The delay distribution is the key number for your protocol. If your hypothesis needs the sound during the first 300 ms of a spindle, count the stimulations inside that window, not the overall recall.
  • Negative delays (stimulation before the labelled onset) happen; the paper counts them as false positives and notes that this "slightly harms our reported results" [1].
  • Raising the threshold trades early stimulations for fewer false ones: precision goes up, the delay distribution shifts right.

Exercises

Why do we need a refractory rule?

In the oscilloscope, note the number of false stimuli after about one minute at the default settings. Restart, set the refractory period to 0 ms and run for the same time. What happens and why?

Answer

With 0 ms, the detector re-arms as soon as one output falls below the threshold, so every flicker of the output inside a spindle (and the disagreement between the eight hidden states) triggers a new sound. In our offline run of the widget's code on 3 minutes of recording 4 (the default) at threshold 0.5, 17 of 17 spindles were stimulated in both cases, but false stimuli went from 0 (400 ms) to 29 (0 ms): the extra sounds land on spindles that were already stimulated, or just after them, so they add no hits, only errors.

How much of a short spindle is left?

With the paper's values in the latency calculator, what fraction of a 0.5 s spindle remains when the sound starts? And of a 2 s spindle?

Answer

The total delay is 40 + 250 + 20 + 4 = 314 ms. For 0.5 s, 186 ms remain (37 %), about 2.4 cycles at 13 Hz; for 2 s, 1686 ms remain (84 %). Short spindles are the hard case for closed-loop stimulation, and the detection delay (not the hardware) is the main term to reduce.

Faster hardware, more hidden states

Suppose your hardware runs the network in 12 ms. With seq_stride unchanged, how many hidden states would simulate() use, and what do you change in the notebook?

Answer

12 ms is 3 samples, so set FPGA_NN_EXEC_TIME = 3: nb_parallel_runs = 42 // 3 = 14 and stride_between_runs = 42 // 14 = 3. Then set network_stride = 3 and nb_samp = 14 in cells 10 and 13, recompute the segment_state_size assertion (14 × 684 = 9576) and the adder (here 14 × 3 = 42, so adder must be 0). Also update constant_delay_s to 0.040 + 0.012 + your stimulus delay. You can check the schedule in the interleaved-states widget with a network stride of 3.
