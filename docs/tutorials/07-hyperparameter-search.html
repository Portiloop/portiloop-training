Hyperparameter search

How many filters, how long a window, how much memory? Instead of guessing, the Portiloop authors let an algorithm (PMBO) train hundreds of candidate networks and keep those that offer the best compromise between detection quality and size. This tutorial explains the idea, what the code does line by line, how to run it, and what to edit first.

Why architecture matters on an embedded device

A detector for closed-loop stimulation is judged on two very different axes. It must detect spindles well, and it must fit and run in real time on small hardware. The paper states the constraint plainly [1]:

Valenchon et al. (2022), section 4“The Portiloop has a limited amount of available memory, so as to ensure its portability and low price. Therefore, large ANN architectures such as SpindleNet [29] are orders of magnitude too large to be implemented in our device. To produce networks that are suitable to our device, we rely on an automated optimization algorithm named “Parallel Model-Based Optimization” (PMBO) that allows us to trade-off accuracy and use of resources on our device”.

Bigger is usually better for accuracy, but every extra parameter costs memory, and every extra multiplication costs time. Time matters twice in closed loop: the forward pass of the published model takes 20 ms on the Portiloop, against 40 ms for the earlier 2-input model [1], and the stimulus can only be sent after the forward pass. The search space is large: tutorial 04 listed about fifteen architecture and training choices, many with dozens of possible values. Training one candidate on the MODA data takes hours on a GPU, so trying everything is impossible.

For neuroscientists: a trade-off you already knowChoosing an fMRI voxel size is the same kind of problem: smaller voxels give better spatial resolution but lower signal-to-noise and longer acquisitions. Nobody asks for “the best voxel size”; one asks for the best resolution for a given scan time, or the shortest scan for a given resolution. The set of protocols that cannot be improved on one axis without losing on the other is exactly what an engineer calls a Pareto front.

Two costs and the Pareto front

PMBO minimizes two costs. In the words of the supplementary material (S1 File, Appendix J) [1]:

  • Software cost: “We cast this into a minimization problem by defining our software cost as \(L_s = 1 - f_1\).” Here \(f_1\) is the F1 score of the trained network on the validation set (tutorial 06).
  • Hardware cost: “we use the number of trainable weights in the ANN as a proxy for these concerns, and call this number our hardware cost \(L_h\).” (The text explains that true memory use and execution time are only known after the model is synthesized on the board, “a lengthy process”.)

Between two trained candidates \(E\) and \(E'\), the paper defines (Definition 1): “We say that \(E\) Pareto-dominates \(E'\) [...] when \(L_s < L'_s \wedge L_h < L'_h\)”, that is, \(E\) is both more accurate and smaller. The Pareto front is the set of candidates that no other candidate dominates; in the paper's words, “all points that are not on the Pareto front have at least one corresponding configuration that is better in terms of both software and hardware cost, and should therefore not be considered.”

Strict or weak domination?The paper's definition requires both costs to be strictly lower. The code is slightly different in one place: update_pareto() refuses a new experiment if an existing front member is lower or equal on both costs (<=), and removes front members that are strictly worse on both. pareto_efficiency() uses strict comparisons, as the paper. The difference only matters for ties, which are rare with real F1 values.

How PMBO searches

The supplementary material introduces the algorithm as follows [1]: “PMBO is essentially a parallelized and evolved version of “Probabilistic SMBO” [2]. PMBO is a guided-search approach that finds a suitable set of hyperparameters rapidly. For this matter, it uses one machine (or process) to train a meta network whose role is to predict non-trivially available costs for any given set of hyperparameters.” SMBO stands for sequential model-based optimization: keep a cheap statistical model (the surrogate, or meta network) of “how good would this configuration be”, use it to decide what to train next, and refit it after every real training.

How a candidate is drawn. If there is no previous experiment, or with probability EPSILON_NOISE = 0.25, every value is drawn uniformly on its grid. Otherwise it is drawn from a Gaussian centred on the previous experiment's (unrounded) values, with a standard deviation of 10 % of each range. The architecture part (window, kernels, strides, dilations) is redrawn, with a growing standard deviation, until the network is valid (nb_out ≥ 1, see tutorial 04), and a configuration identical to one already tried (same_config_dict()) is rejected. The paper calls these two kinds of randomness “noise type 1” (0.25) and “noise type 2” (0.1, below) [1].

“The previous experiment” is the last network actually trained. In the local loop it is kept in a variable initialized once, before the loop, and updated after every training:

    prev_exp = {}  # last trained experiment, used to sample new configurations around it

        ...
            config_dict, unrounded = sample_config_dict(name=RUN_NAME + "_" + str(num_experiment), previous_exp=prev_exp, all_exp=all_experiments)
        ...
        prev_exp = exp

Step 2: the hardware filter

def nb_parameters(config_dict):
    net = PortiloopNetwork(config_dict)
    res = sum(p.numel() for p in net.parameters())
    del net
    return res

Each candidate network is instantiated (not trained) only to count its parameters, exactly as in the calculator of tutorial 04. Candidates outside MIN_NB_PARAMETERS = 1,000 and MAX_NB_PARAMETERS = 80,000 (Utils/utils.py) are discarded and resampled. This range is the “range cost hardware 1000-80000” of the paper's supplementary Table I. Change it first if your hardware differs: it is the only place where the device's capacity enters the search.

Step 3: the surrogate model

Training a candidate costs hours; predicting its cost from its configuration costs microseconds. The surrogate is a small fully connected network (three nn.Linear layers, 10 inputs, 200 hidden units, 1 output):

def transform_config_dict_to_input(config_dict):

         #int(config_dict['RNN']),
         #int(config_dict['envelope_input']),
         config_dict["lr_adam"],
         config_dict["batch_size"]]

It is trained by train_surrogate() to predict cost_software (\(1 - F_1\), because MAXIMIZE_F1_SCORE = True in Utils/utils.py) from these 10 numbers, with mean squared error, plain SGD (learning rate 0.05, weight decay 0.01, gradient clipping at 10) and one experiment per batch. With 100 experiments or fewer it trains on all of them for as many epochs as there are experiments; above START_META_TRAIN_VAL_AFTER = 100 it keeps 20 % aside as a validation set and stops after META_EARLY_STOPPING = 30 epochs without improvement (at most MAX_META_EPOCHS = 500). A fresh surrogate is trained from scratch after every completed experiment.

For neuroscientists: a surrogate is a fitted dose-response curveIf each experiment were a costly session with a participant, you would not test stimulation intensities at random: you would fit a dose-response curve to the sessions run so far and use it to choose the next intensity. The surrogate plays the role of that curve, in 10 dimensions instead of one. Like any curve fitted to few points, it is unreliable where no data has been collected yet, which is why the algorithm keeps some randomness.
The inputs are not normalizedThe 10 inputs have very different scales (lr_adam around 0.0005, batch_size up to 256, window up to 124 samples) and are fed to the surrogate raw. In the rehearsal run below, the first surrogates predicted costs of 5.5, −29.1 and −1.6 (a cost \(1 - F_1\) must lie between 0 and 1) before settling once about eight experiments were available. If you modify the code, standardizing these inputs is a natural first improvement. The paper also reports that “the predictions of the meta-learner are often near-constant in well-performing areas of the search space” and that the authors “surmise that this is due to the large variance in model performance from one training session to another” [1].

Step 4: choosing one candidate out of 200

With probability EPSILON_EXP_NOISE = 0.1 (and always while the front is empty) a random candidate is chosen. Otherwise each candidate \(\hat E\), with its predicted software cost \(\hat L_s\) and its exact hardware cost \(L_h\), receives the heuristic “Pareto efficiency” of the supplementary Appendix J [1], computed against the set \(\mathcal E\) of experiments already completed:

$$\eta(\hat E) = \underbrace{1 - \frac{d_{\mathcal E}(\hat E)}{|\mathcal E|}}_{a:\ \text{not dominated}} + \underbrace{\frac{D_{\mathcal E}(\hat E)}{|\mathcal E|}}_{b:\ \text{dominates others}} + \underbrace{\frac{\min L_s}{\hat L_s}}_{s:\ \text{beats the best F1?}} - \underbrace{h_{\mathcal E}(\hat E)}_{\text{crowding penalty}}$$

where \(d\) counts the completed experiments that would dominate the candidate and \(D\) those it would dominate. The crowding penalty \(h\) is the density of completed experiments in the candidate's parameter-count bin (100 bins over 0 to 80,000), multiplied by the range width: it equals 100 times the fraction of past experiments that fall in the same 800-parameter bin. It is large compared with the other terms (a, b and s are of order 1), so in practice candidates in parameter ranges that have not been tried yet win; this spreads the trainings along the size axis. The code:

    score_not_dominated = 1.0 - float(nb_dominating) / len(all_experiments)
    score_dominating = nb_dominated / len(all_experiments)
    score_distance_from_best_loss = abs(best_cost_software / experiment[
        "cost_software"])  # The lower is the predicted experiment loss, the better. This score is close to 1 when you reach a loss as good as the lowest one of all exp. If yours is better, then the score will be above 1. Otherwise the farest you are, the lower is your score
    ...
    return score_dominating + score_not_dominated + score_distance_from_best_loss
        histo = np.histogram([exp["cost_hardware"] for exp in all_experiments], bins=100, density=True, range=(0, MAX_NB_PARAMETERS))
        ...
            efficiency = pareto_efficiency(exp, all_experiments)
            ...
            nerf = histo[0][min(idx, len(histo[0]) - 1)] * MAX_NB_PARAMETERS

Known issue: predicted costs near zero or negative dominate the choiceThe term \(s = |\min L_s / \hat L_s|\) explodes when the surrogate predicts a cost close to 0, and the absolute value turns a (meaningless) negative prediction into a large positive score. In the rehearsal below, a candidate predicted at −0.00027 received a score of 1,559 (typical scores are 2 to 4). Clipping predictions to the interval 0 to 1 before scoring would avoid this.

Why bother with a surrogate? A toy experiment

The widget below is a toy: two made-up hyperparameters (“width” and “window”), a made-up F1 landscape with a narrow good region and a misleading bump, and a made-up parameter count. A “training” takes no time here: it just reads the landscape and adds noise. It compares random search (train one random configuration per iteration) with a PMBO-like strategy: draw N candidates (25 % uniformly, 75 % around the last trained point), predict their F1 with a kernel regression of the points trained so far (a simple surrogate, not the neural network of the real code), and train the candidate with the best score \(\eta\) computed exactly as above, crowding penalty included, with a 10 % chance of a random pick.

What the toy shows (averages over 40 seeds with the default settings, measured while building this page): during the first ten trainings the guided search is no better than random, because the surrogate has almost nothing to learn from and the crowding penalty forces exploration. After about 20 trainings it pulls ahead: with N = 50 its gap after 30 trainings (about 0.03) is roughly half that of random search (about 0.06), and random search has still not reached it after 60 trainings. With very noisy trainings the surrogate is misled more often. The real search space has 10 dimensions instead of 2, where blind sampling generally needs many more trainings to stumble on good regions, but the paper's remark about near-constant predictions is a reminder that the surrogate is only as good as the reproducibility of the trainings it learns from.

The selected configuration is trained by the same run() function as in tutorial 05, with save_model=False: no checkpoint is kept during the search, only the score. The software cost is \(1 - \) the best validation F1 reached during that training. The experiment is added to the front if no front member is at least as good on both costs, and the surrogate is retrained. After every iteration the two lists are pickled and a W&B plot of the front is logged.

Rehearse the search without a GPU

A real search costs days of GPU time, so make sure the machinery works first. The script below runs the genuine PMBO loop (sampling, size filter, surrogate, selection, pickles) but replaces the training function by a fake one that returns a made-up F1 instantly. It needs neither the dataset nor a GPU, and it writes to a temporary folder.

  1. Install the requirements (tutorial 02, pip install -e . from the repository root, which also installs wandb).
  2. Save this file at the repository root as rehearse_pareto.py: 
    # rehearse_pareto.py: exercise the PMBO loop without training any network.
# Run from the repository root:  WANDB_MODE=disabled python3 rehearse_pareto.py

import random
import tempfile
from pathlib import Path

    logging.getLogger(noisy).setLevel(logging.WARNING)

    n = ps.nb_parameters(config_dict)
    f1 = min(0.75, 0.45 + 0.06 * (n / 10000) ** 0.5) + random.gauss(0, 0.02)
    return 1 - f1, f1, 0

Running a real search on one machine

  1. Prepare the data and a GPU. The MODA dataset files must be in portiloop_software/dataset/ (tutorial 02), and a single training from tutorial 05 should already work on this machine.
  2. Update your clone (git pull; the fixes described in the “Older clones” notes date from November 2026), and go through the table of hard-coded constants (at least PARETO_ID, the parameter range, the training budget).
  3. Choose how to log. With an account: wandb login (set WANDB_ENTITY to log into a team). Without one: WANDB_MODE=offline keeps the search plot and every candidate's learning curves in ./wandb/ (upload later with wandb sync), or WANDB_MODE=disabled records nothing (the pickles are still written). In clones older than November 2026, offline mode stopped every training with UsageError: No API key configured (raised by the W&B restore step of run(), which now ignores that error); git pull if you see it.
  4. Launch from the repository root, in a session that survives logout (tmux, screen, or a SLURM job): 
    python3 -m portiloop_software.portiloop_python.PMBO.pareto_search --output_file pareto_tests.log
    --output_file sends the log to a file (otherwise it goes to the terminal). Each iteration trains one network for up to 150 epochs of 1,000 batches, so expect hours per iteration on one GPU. The search can be interrupted and restarted: at start-up it reloads the pickles of the same RUN_NAME (log line existing meta dataset loaded), retrains the surrogate and continues.

Distributed search: server, meta-learner, workers

This is the “parallel” in PMBO, the setup the paper used on 20 GPUs. pareto_network.py has three roles, chosen by a flag:

    parser.add_argument('--server', action='store_true')
    parser.add_argument('--meta', action='store_true')
    parser.add_argument('--worker', action='store_true')
    parser.add_argument('--output_file', type=str, default=None)
    parser.add_argument('--ip_server', type=str, default=IP_SERVER)
  • The server only relays messages. It listens on TCP port 6666 for the meta-learner and 6667 for workers, keeps a queue of up to LEN_QUEUE_TO_LAUNCH = 20 selected configurations, hands one to each idle worker and forwards finished results to the meta-learner.
  • The meta-learner owns the pickles, the surrogate and the W&B log. Whenever the server asks for work or sends results, it updates the front, retrains the surrogate and selects one new configuration (Steps 1 to 4).
  • Each worker trains the configuration it receives with run() (Step 5) and sends back the result, including the surprise.
Security: run the distributed search only on a network you trust

The three roles exchange Python pickles over plain TCP, with no password, no encryption and no check of who is connecting. Every message is decoded with pickle.loads:

    send_ack(sock)
    return pickle.loads(msg)

Decoding a pickle can execute arbitrary code. Anyone who can open a connection to the server's ports can therefore run programs on the server, and through the server on the meta-learner and on every worker, which decode the server's messages the same way. The server listens on all network interfaces of its machine (it binds to the empty address ''), on TCP ports 6666 and 6667.

  • Use a private network you control (an isolated cluster network, a lab network or a VPN). Never expose ports 6666 and 6667 to the internet, nor to a shared network with users you do not trust (a campus network, a multi-user login node).
  • Close the ports to everyone else. For example, with ufw on the server, allow only your own subnet, then deny the rest: 
    sudo ufw allow from 10.0.0.0/24 to any port 6666:6667 proto tcp
sudo ufw deny 6666:6667/tcp
  • Machines on different networks: use an SSH tunnel instead of opening the ports. With the ports closed to the outside as above, run on each meta-learner and worker machine: 
    ssh -N -L 6666:localhost:6666 -L 6667:localhost:6667 you@server-address
    then start the role with --ip_server 127.0.0.1. The traffic travels encrypted inside SSH and reaches the server on its loopback interface, so only people with an SSH account on the server can connect.
  • The result files are pickles too. Only load .pkl files from portiloop_software/pareto/ (for example with inspect_pareto.py below) if you produced them yourself.
  1. Start the server on a machine reachable by all others (ports 6666 and 6667 reachable from your own machines only, see the security warning above): 
    cd /path/to/portiloop-training
python3 portiloop_software/portiloop_python/PMBO/pareto_network.py --server --output_file server.log
  2. Start the meta-learner (one, anywhere; CPU is enough), giving the server address: 
    python3 portiloop_software/portiloop_python/PMBO/pareto_network.py --meta --ip_server 10.0.0.5 --output_file meta.log
  3. Start one worker per GPU on machines that have the dataset: 
    CUDA_VISIBLE_DEVICES=0 python3 portiloop_software/portiloop_python/PMBO/pareto_network.py --worker --ip_server 10.0.0.5 --output_file worker0.log
CUDA_VISIBLE_DEVICES=1 python3 portiloop_software/portiloop_python/PMBO/pareto_network.py --worker --ip_server 10.0.0.5 --output_file worker1.log
    Replace 10.0.0.5 by your server's address. Workers can join at any time and reconnect automatically after a connection loss; a worker stopped in the middle of a training loses that experiment (the meta-learner does not re-queue it).
Warnings for the distributed mode
  • Run it as a script, not with python -m. pareto_network.py imports its neighbours as top-level modules (from pareto_network_server_utils import ..., from pareto_search import ...), which only works when the script's own folder is on the import path. With python3 -m portiloop_software...pareto_network it fails with ModuleNotFoundError: No module named 'pareto_network_server_utils' (checked). The package itself must be installed (pip install -e .).
  • Extra dependencies: requests and pyinstrument (both in setup.py).
  • Internet access: every role calls http://api.ipify.org (an external service) at start-up to print its public IP address, which also tells that service the machine is running; on a cluster node without internet access this call fails. Remove the self.public_ip = get(...) lines if needed.
  • Security: see the warning above before starting any role.
  • Pickle and W&B files are written by the meta-learner only, in its own portiloop_software/pareto/.
Duplicate resultsIf the meta-learner receives a result for a configuration it already has (rare, since same_config_dict() rejects duplicates when sampling), it keeps the better of the two software costs and updates the front with that experiment. Clones older than November 2026 crashed on this path (misspelled key "software_cost"); git pull fixes it.

Troubleshooting
  • KeyError: 'validation_network_stride' at the first training: your clone predates the fix; git pull.
  • AssertionError: CUDA unavailable: no GPU visible; the devices are hard-coded to cuda:0.
  • FileNotFoundError on dataset_classification_full_big_250_matlab_standardized_envelope_pf.txt or subject_sequence_full_big.txt: the dataset is not installed (tutorial 02).
  • The log is flooded with score dominating lines: these are print() calls in pareto_efficiency(), 600 lines per iteration; filter them with grep -v.
  • A new search “remembers” old results: the pickles of the same PARETO_ID were found and reloaded. Change PARETO_ID or move the old files.

What the search found in the paper

Everything in this section is quoted from Valenchon et al. (2022) [1]; the repository does not contain the search logs.

  • Scale of the final search: “we run PMBO on 20 Tesla V100 GPU workers over a period of 24h.” The PMBO settings (supplementary Table I) were a hardware range of 1000-80000, noise type 1 of 0.25, noise type 2 of 0.1, \(m = 200\), and a 3-layer MLP meta network of hidden size 200 trained with SGD (learning rate 0.05, weight decay 0.01): the values found in the current code.
  • Choice of the model: “We select the best model in terms of software cost (i.e. the one with the highest classification performance) irrespective of its hardware cost i.e., the model corresponding to the right-hand end of the Pareto front. This model is acceptable because it is anyway rather small, with only 25.6k parameters. We measure the execution time of this architecture to be 20 ms per forward pass on the Portiloop (vs. 40 ms for the 2-input version).”
  • The time between windows of one memory chain was chosen by the search: “the time-dilation (set to 168 ms by PMBO)”. Supplementary Table II marks batch size, learning rate, window size, time dilation and all architecture hyperparameters as chosen by PMBO.
  • A first search (with the envelope as a second input) produced the 2-input model; an ablation then showed that the envelope could be dropped, and PMBO was run “one more time to devise our final Pareto-optimal ANN architecture, now with only the cleaned signal as input.”
  • Limits: “the predictions of the meta-learner are often near-constant in well-performing areas of the search space, suggesting that the meta-model could not further predict the software cost. In other words, we were unable to differentiate between the best-performing configurations of the neural network.” The supplementary Fig 1 caption adds that part of each window is ignored by the model, “Therefore, it is probably possible to shrink our model even more, although PMBO did not find this.”

The names of the shipped checkpoints, pareto_search_15_35_v4_<i>, follow the naming pattern of the search code (RUN_NAME + "_" + number), but the repository does not document what “15”, “35” and “v4” refer to.

Exercises

Dominated or not?

Three trained networks: A has 12,000 parameters and F1 = 0.66; B has 30,000 parameters and F1 = 0.70; C has 25,000 parameters and F1 = 0.64. Which are on the Pareto front? Which would you deploy on a device that holds at most 20,000 parameters? And at most 40,000?

Answer

C is dominated by A (fewer parameters and higher F1). A and B are on the front: neither is both smaller and better than the other. Budget 20,000: only A fits. Budget 40,000: B (best F1 within budget), unless the 4-point F1 difference is within the training-to-training variability, in which case A's lower cost (and faster forward pass) may be the wiser choice.

Compute the crowding penalty

After 50 completed experiments, 5 have between 24,000 and 24,799 parameters. A candidate has 24,500 parameters. What penalty \(h\) does exp_max_pareto_efficiency() subtract from its score, and what does that mean for its chances?

Answer

The bins are 800 parameters wide (80,000 / 100); this candidate is in the bin 24,000 to 24,799. The density is \(5 / (50 \times 800)\), multiplied by 80,000: \(h = 100 \times 5/50 = 10\). Since the other three terms are of order 1 (unless the predicted cost is near 0), a candidate in an empty bin (\(h = 0\)) will almost always be preferred: the search deliberately spreads its trainings over model sizes.

Plan a search for your hardware

Your embedded board can hold at most 15,000 parameters, and you want to know whether the envelope input helps at that size. List the edits you would make before launching.

Answer

In Utils/utils.py: MAX_NB_PARAMETERS = 15000; envelope_input_range_t = [0, 1, 1]; possibly reduce MAX_EPOCHS_PER_EXPERIMENT to save time. In pareto_search.py: a new PARETO_ID; uncomment int(config_dict['envelope_input']) in transform_config_dict_to_input() and set nb_features = 11 in SurrogateModel so the surrogate can tell the two kinds of networks apart. Note that the 2-input branch doubles the convolutional and GRU parameters (tutorial 04), so under a 15,000 budget the 2-input networks must be much narrower. Then rehearse with the fake trainer before using GPUs.
